# ADR 0015: Power BI report (rpt_hubops) -- real quirks hit building and deploying it

**Status:** done, 2026-11-01.

## Context

Phase 5's report half needed 4 pages (Hub Scorecard, Bank Performance,
Turn Performance, Delay Root Cause) on `sm_hubops`, built headless (no
Power BI Desktop in this environment) via
`@microsoft/powerbi-report-authoring-cli`. Per that skill's own guidance
for full-report builds, the pages were generated by a deterministic
Node script (`scripts/fabric/build_report.js`) rather than hand-edited
PBIR JSON. Several real problems surfaced building and deploying it.

## 1. Headless rendering verification is possible without Desktop

`powerbi-report-author preview --host service --group <workspaceId>
--dataset <semanticModelId> --headless --screenshot <path> --all-pages`
renders a PBIR report against **live data** from the actual deployed
Fabric semantic model, in a headless browser, no Power BI Desktop
needed. This made full visual verification possible in a CLI-only
environment -- every page was screenshot-reviewed against real query
results before being considered done, not just schema-validated.

## 2. `filterConfig` is a sibling of `visual`, not a property inside it

Nesting a visual-level `filterConfig` inside the `visual` object (by
analogy with `objects`/`visualContainerObjects`, which *are* inside
`visual`) fails `powerbi-report-author validate` with `/visual must NOT
have additional properties (property: "filterConfig")`.
`filterConfig` belongs at the visual-container root, as a sibling of
`name`, `position`, and `visual`.

## 3. Reusing one filter object across pages/visuals produces duplicate filter names

Generating a single `categoricalFilter(...)` object once and reusing
that same object reference for the page-level filter on two different
pages produces the same `Filter<hex>` name twice, caught by `validate`
as `PBIR_FILTER_NAME_DUPLICATE_GLOBAL`. Filter names must be unique
across the *entire report definition*, not just per scope -- the
generator now calls `categoricalFilter(...)` fresh at each use site
rather than hoisting it to a shared constant.

## 4. A plain column bound as if it were a measure renders `Missing_References`, not a schema error

`Bank[Peak Avg Flights]` is a plain Direct Lake column, not a measure.
Binding it to a chart's `Y` role via a `Measure` field expression
(copy-pasted from a different chart that legitimately used measures)
validates cleanly -- `powerbi-report-author validate` has no way to
know the model doesn't have a measure by that name -- but fails at
render time: `RENDER_FAILED` / `Missing_References`, "Could not render
a report visual." Fixed by using an `Aggregation` expression (`Function:
1` / Average) wrapping the column instead. **Validation passing is not
proof a visual's field bindings are correct against the live model** --
only a real render (§1) catches this class of bug.

## 5. The same Origin/Dest RLS conflict from ADR 0014 recurs at the report-filter layer

The Turn Performance page's "Worst Routes Into DFW" table needs `Dest =
DFW, Origin = anything`. It originally sat under a page-level filter of
`Airport[Airport Key] = DFW` (meant to scope the page's *other*
visuals, which relate to `Airport` only via Origin/Station). Page
filters and visual filters combine with AND, so the table ended up
filtered to `Origin = DFW AND Dest = DFW` -- empty, same structural
conflict ADR 0014 hit in DAX, just at the PBIR filter layer instead.
Rendered as a table with headers but zero rows (no error -- another
reason § 1's live-render check matters, not just `validate`). Fixed by
removing the page-level filter and applying station scoping per-visual
instead: the two Aircraft Turn charts each get their own `Airport =
DFW` visual filter (fine -- Aircraft Turn relates to Airport only via
Station, no Dest ambiguity), and the routes table keeps only its
`Airport (Dest) = DFW` filter, unconflicted.

## 6. Fabric's Report import rejects a `byPath` semantic-model reference

`definition.pbir`'s `datasetReference.byPath` (pointing at the
co-located `sm_hubops.SemanticModel` folder) is schema-valid and
`powerbi-report-author validate` passes it -- it's the right choice for
a *local* PBIP pointing at a *local* semantic-model folder. But
`az rest POST /v1/workspaces/{id}/reports` with a packed payload using
`byPath` fails after accepting the job: *"Report Workload failed to
import the report... definition.pbir holds the relative path (ByPath)
reference to the semantic model. Fabric REST API only supports
byConnection references."* Real Fabric-API-specific constraint, not in
the public PBIR JSON schema (which documents both as valid, and they
are -- for Desktop). Confirmed no orphaned item was left behind by the
failed import (`GET .../items?type=Report` returned empty) before
retrying.

## 7. `byConnection` needs the semantic model's GUID inside the connection string, not just its name

First `byConnection` attempt used `Data Source=powerbi://api.powerbi.com/v1.0/myorg/AmericanAirlines;Initial
Catalog=sm_hubops` (workspace + dataset *names*, the same form the
`powerbi-modeling-mcp` tool's own `ConnectFabric` operation accepts).
Fabric's Report import rejected it: `InvalidConnectionInformation` --
*"Ensure that a valid GUID is provided either in
'byConnection.pbiModelDatabaseName' or as the 'semanticModelId'
parameter within 'byConnection.connectionString'."* Fixed by appending
`;semanticModelId=<sm_hubops item GUID>` to the connection string. The
working value: `Data Source=powerbi://api.powerbi.com/v1.0/myorg/AmericanAirlines;Initial
Catalog=sm_hubops;semanticModelId=9fc47519-9010-455f-977f-d201c18f94e3`.

## Consequences

- `rpt_hubops` is live in the `AmericanAirlines` workspace (id
  `d8404b97-b98a-4228-97cf-3b86824de65c`), 4 pages, all verified against
  live data with zero render failures after the fixes above.
- **Any future Fabric Report deployed via `az rest` (not just this one)
  needs `byConnection` with an explicit `semanticModelId` in the
  connection string** -- `byPath` and a bare name-based connection
  string both fail import, silently-ish (only surfaces after the job
  is accepted and run, not at payload-build time).
- `scripts/fabric/build_report.js` is the reusable generator for any
  future pages (5-8, Phase 8) -- extend its helper functions rather
  than hand-authoring new PBIR JSON.
